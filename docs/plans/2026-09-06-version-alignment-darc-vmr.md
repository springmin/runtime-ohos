# Version alignment strategy for the OHOS forks (darc/VMR study)

**Date:** 2026-09-06 (device side)
**Context:** round-21/22 hit aspnetcore↔SDK version skew
(SDK pins Microsoft.AspNetCore.App at 11.0.0-rc.1.26452.110 from its
eng/Version.Details.xml tracking dotnet/dotnet Sha 11e3a8dcce; aspnetcore-ohos
published only 26451.109 from Sha f2b969981e). Workaround: re-versioning the
aspnetcore nupkg to the SDK's restore key (round-21). This doc records how
UPSTREAM keeps versions aligned (darc/VMR) and the pragmatic strategy for our
manually-built forks.

## 1. Upstream architecture: Unified Build + VMR

dotnet/dotnet (the VMR - Virtual Monolithic Repository) is the single place
that builds the official product. ~25 product repos (runtime, sdk, aspnetcore,
roslyn, ...) sync into it as subdirectories; src/source-manifest.json records
the exact commitSha of each component at every VMR commit.

Two-way code flow between each product repo and the VMR (Maestro service,
dotnet-maestro[bot] PRs):

- **Forward flow** (repo -> VMR): source diffs from a product repo are applied
  onto the VMR's src/<component> directory.
- **Backflow** (VMR -> repo): PR titled "[branch] Source code updates from
  dotnet/dotnet" carrying (a) version-file updates (eng/Version.Details.xml +
  the Maestro-generated eng/Version.Details.props), (b) binaries/intermediate
  packages built by the VMR build, and (c) any VMR-side source changes.
  This is the "flat flow" model - repos depend on the VMR, not on each other.

## 2. How versions stay aligned (the key property)

- Every product repo's eng/Version.Details.xml has a SINGLE Source
  (Uri=https://github.com/dotnet/dotnet + Mapping=<repo> + Sha) - the last
  VMR commit synced. Example (our forks):
  - sdk: Sha 11e3a8dcce -> aspnetcore/runtime versions 26452.110
  - aspnetcore: Sha f2b969981e -> runtime 26451.109
- Maestro regenerates eng/Version.Details.props from the xml
  ("auto-generated by the Maestro dependency flow system"). sdk's build reads
  it via src/Tasks/sdk-tasks/GetDependencyInfo.cs +
  src/Layout/redist/targets/GenerateBundledVersions.targets to produce
  Microsoft.NETCoreSdk.BundledVersions.props (the KnownFrameworkReference /
  ILCompilerPackVersion table the SDK resolves at restore).
- Because all components take their dependency versions from the SAME VMR
  commit, runtime/aspnetcore/sdk versions never drift upstream: when the VMR
  moves, every repo's backflow PR updates its Version.Details to the same new
  Sha, and the VMR build produces all packages at mutually-consistent
  versions.

## 3. Why our forks drift

We do NOT use Maestro/VMR backflow. Each fork independently merges
dotnet/dotnet main ("Merge remote-tracking branch 'origin/main'" commits at
different times). The VMR main advances continuously, so:

- sdk fork merged a state where aspnetcore darc version = 26452.110
- aspnetcore fork merged a state where its runtime dep = 26451.109
- One VMR cycle of skew appears between the SDK's expected aspnetcore version
  and what aspnetcore-ohos builds/publishes.

Also: we build each repo standalone (not in the VMR), so the VMR's
"single build produces everything consistent" property does not hold for us.

## 4. Options for our forks

### Option A - VMR-baseline alignment (upstream-correct, heavy)
Sync all three forks to the SAME dotnet/dotnet commit before each release
cycle (same Sha in all three eng/Version.Details.xml), then build runtime ->
aspnetcore -> sdk. This reproduces the VMR's consistency without using the
VMR itself. Cost: merging the single dotnet/dotnet repo or carefully
coordinating three main merges; conflicts compound.

### Option B - version-parameterized build order (pragmatic, recommended)
Fix the build order and let each downstream repo take the upstream repo's
ACTUAL published version instead of its own Version.Details value:

1. Build + publish runtime-ohos (produces X, e.g. 26451.109).
2. Build aspnetcore-ohos with its runtime dependency overridden to X
   (/p:MicrosoftNETCoreAppRefPackageVersion=X etc. or edit
   eng/Version.Details.props before build) - publish aspnetcore at X.
3. Build sdk-ohos with aspnetcore + runtime overridden to X. If the SDK's
   BundledVersions still pins a version Y != X that no package exists for
   (like 26452.110 vs published 26451.109), re-version the aspnetcore
   nupkg to Y (round-21 approach) OR - better - override the SDK's
   Version.Details.props values at build time so the generated
   BundledVersions matches what we publish.

Automate the re-version step (round-21 was manual): a small script that takes
a published nupkg + target version, rewrites the nuspec version and repacks.

### Option C - track one VMR commit across forks (medium-term)
Instead of merging dotnet/dotnet main at arbitrary times, pin all three forks
to the same dotnet/dotnet release/main commit per build cycle. Reduces the
skew to zero at the source. Requires discipline: record the synced VMR Sha
(similar to source-manifest.json) in each fork and merge in lockstep.

## 5. Recommendation

- Short term: keep Option B. Formalize: (a) fixed build order
  runtime -> aspnetcore -> sdk; (b) version-override properties in the build
  scripts of aspnetcore and sdk; (c) scripted nupkg re-versioning instead of
  the manual round-21 step.
- Medium term: Option C - record and coordinate the dotnet/dotnet Sha that
  all three forks merge, so Version.Details.xml values are mutually
  consistent and re-versioning becomes unnecessary.

## 6. Local mechanism map (verified in our forks)

- eng/Version.Details.xml: single Source dotnet/dotnet + Mapping + Sha
- eng/Version.Details.props: Maestro-generated version table (do not hand-edit
  - regenerated by automation upstream; we hand-edit only as a fork override)
- sdk: src/Tasks/sdk-tasks/GetDependencyInfo.cs reads the xml;
  src/Layout/redist/targets/GenerateBundledVersions.targets turns it into
  Microsoft.NETCoreSdk.BundledVersions.props (KnownFrameworkReference table);
  in VMR mode (DotNetBuildFromVMR=true) the xml is not read (versions come
  from the VMR build itself).
- aspnetcore: eng/Version.Details.props MicrosoftNETCoreAppRefPackageVersion
  drives which runtime ref it builds against.

## 7. Review + supplement (build side, 2026-09-06)

Reviewed against the SDK's actual override surface. Key finding: **Option B
can avoid the re-version hack entirely for the SDK side.**

### 7.1 SDK aspnetcore override point (better than re-versioning)

The SDK's aspnetcore KnownFrameworkReference chain is overridable:
- eng/Version.Details.props: `MicrosoftAspNetCoreAppRefPackageVersion`
  (= 26452.110, darc) -> `MicrosoftAspNetCoreAppRuntimePackageVersion`
  (defaults to Ref when empty — Directory.Build.props `== ''` guard).
- GenerateBundledVersions.targets: `KnownAspNetCorePack
  AspNetCorePackVersion="$(MicrosoftAspNetCoreAppRuntimePackageVersion)"`.

=> Passing `/p:MicrosoftAspNetCoreAppRuntimePackageVersion=$rtver` (26451.109)
to the SDK build makes the SDK's restore resolve OUR published aspnetcore
(26451.109, uploaded round-20) — no 26452.110 re-version needed. The round-21
nupkg re-versioning remains only as a fallback if the override is insufficient
(covered by the =='' guard it is not).

Applied to build-ohos-all.sh stage4 (sdk) alongside the existing
Host/Runtime overrides.

### 7.2 Scripted nupkg re-versioning (round-21 fallback, automated)

`reversion-nupkg.py <in.nupkg> <old-version> <new-version>` — rewrites nuspec +
nupkg.metadata versions and repacks (used for the ILLink.Tasks and aspnetcore
26452.110 uploads). Kept for edge cases the SDK override cannot cover.

### 7.3 Option C concretization (medium term)

Record a single dotnet/dotnet Sha per build cycle across the three forks
(mirror of VMR source-manifest.json). Mechanism:
- Pick the dotnet/dotnet commit to sync (release/main).
- Merge it into runtime-ohos first; record Sha in a per-fork marker
  (e.g. eng/ohos-vmr-sha.txt).
- Merge the SAME Sha into aspnetcore-ohos + sdk-ohos within the cycle so
  Version.Details.xml values are mutually consistent (aspnetcore/runtime deps
  and SDK's aspnetcore/runtime pins all derive from one VMR state).
- Release after all three merged the same Sha — version skew goes to zero at
  the source; no overrides/re-versioning needed.

### 7.4 Remaining review notes
- Runtime/aspnetcore override in the script already pins the runtime dep;
  the new aspnetcore override closes the SDK side. The script's fixed order
  (runtime -> aspnetcore -> sdk) is Option B's formalized build order.
- Risk: `MicrosoftAspNetCoreAppRuntimePackageVersion` also drives the SDK's
  own bundled aspnetcore assets when IncludeAspNetCoreRuntime=true — we build
  with =false, so overriding it only affects the KnownFrameworkReference
  restore key (desired). Document if we ever flip IncludeAspNetCoreRuntime.
