## FAIL: 109 NativeAOT single-file ilc cannot start on device

Symptom (both direct run and SDK IlcCompile exec):
```
The library 'libhostpolicy.so' required to execute the application was not
found in '/storage/Users/currentUser/.dotnet'.
Failed to run as a self-contained app.
  - ran as self-contained because 'ilc.runtimeconfig.json' was not found.
```
Adding a runtimeconfig that specifies the Microsoft.NETCore.App framework
changes the error to "did not specify a framework" - the bundle-internal
config conflicts with the external file.

Diagnosis:
1. ilc is a NativeAOT single file (7.85MB, NEEDED libc.musl only, .codesign
   present, contains hostfxr_main_bundle_startupinfo strings).
2. It embeds an AssemblyDependencyResolver call (ilc resolves assemblies at
   compile time) which requires hostpolicy.
3. With no runtimeconfig it is treated as self-contained; the bundle's fx
   resolver then looks for hostpolicy under DOTNET_ROOT (~/.dotnet), where
   libhostpolicy.so does not exist (it lives in
   shared/Microsoft.NETCore.App/<ver>/ - not found by the root lookup).
4. Host policy lookup fails -> exit 131.

Suggested build-side fixes (any one):
- Publish ilc as framework-dependent (ship ilc.runtimeconfig.json pointing at
  the Microsoft.NETCore.App framework), OR
- Embed hostpolicy in the single-file bundle, OR
- Verify how the official linux-musl ilc pack (the shape 109 mirrors) starts
  on Linux and replicate; note Linux dotnet SDK layout puts libhostpolicy.so
  reachable from DOTNET_ROOT via host/fxr resolution, while on-device the
  shared framework layout differs.

## Round-15 follow-up (2026-09-05): hostpolicy fix (方案 A) partially verified

Build-side round-15 (sdk `6373e091d0`) deploys libhostpolicy.so to the
DOTNET_ROOT root from install-dotnet-ohos.sh. Device applied the equivalent
manually (copied shared/.../11.0.0-rc.1.26451.109-r2r/libhostpolicy.so to
~/.dotnet/libhostpolicy.so) and re-tested the 109 single-file ilc.

Result: progress but NOT fixed:
- Error changed from exit 131 ("libhostpolicy.so not found") to exit 137
  ("Failed to bind to CoreCLR at ''", HRESULT 0x80008088).
- Root cause of the remaining failure: the 109 ilc package is a CoreCLR
  self-contained single-file apphost (toolAot.targets PublishSingleFile=true
  because OHOS is excluded from NativeAOT at eng/Subsets.props:59) but the
  nupkg ships only: ilc + libjitinterface_arm64.so + 5 libclrjit_*_arm64.so +
  libc++_shared.so. Missing: libcoreclr.so (and the CoreCLR single-file
  publish layout normally keeps native .so files alongside the apphost on
  Linux). No bundle marker in ilc; PDB paths show
  ILCompiler_publish/ohos.arm64.Release/linked/ layout.
- Round-9 split layout (26451.1, 64 files: ilc apphost + ilc.dll +
  ilc.deps.json + managed dlls, framework-dependent) remains the only shape
  that has PASSED on device. The 26451.109 single-file shape cannot start
  with just hostpolicy deployed; it needs the complete self-contained
  runtime set (coreclr + hostfxr + managed payload) either in the nupkg or
  resolvable from the installed framework.

Suggested build-side fixes (round-16):
1. Ship the full CoreCLR single-file publish output in the ilc nupkg
   (libcoreclr.so + libhostfxr.so + managed single-file payload) - i.e. what
   a Linux PublishSingleFile self-contained output actually contains, OR
2. Revert ilc to the round-9 framework-dependent split layout (64 files,
   known to pass on device), OR
3. Enable NativeAOT for the OHOS ilc tool build (UseNativeAotForComponents)
   so the tool is a real NativeAOT single file (no host needed), matching
   the macOS pattern round-15 studied - requires Subsets.props:59 to allow
   OHOS for the tool build.

## Round-16 follow-up (2026-09-05): split-layout ilc verified — ilc runs, AOT output crashes

Build-side round-16 replaced the single-file asset with the round-9 split
layout (64 tools/ files, 16.7MB nupkg: 31KB apphost + ilc.dll +
ilc.runtimeconfig.json (includedFrameworks self-contained) + libcoreclr.so/
libhostfxr.so/libhostpolicy.so + 20 .so, all .codesign-signed). Device results:

1. **ilc itself RUNS** (exit 0, --help works) — split layout + included
   frameworks + hostpolicy in-package resolves the round-15 exit 131/137
   failures. The single-file shape's host resolution problem is gone.
2. **AOT publish through the SDK succeeds** (IlcToolsPath pointed at the new
   tools dir; "Generating native code" completes, exit 0).
3. **The published AOT app CRASHES at startup (exit 139, SIGSEGV)** — even a
   minimal app (pure libc write(2), no runtime API calls). Reproduced with
   both the 109 runtime packs AND the 26451.1 packs (IlcToolsPath forced), so
   the crash is caused by the 109 ilc compile, not the runtime pack.

Control: the identical source published with the 26451.1 ilc (stock SDK pack)
runs fine (exit 0). 109 ilc output is ~1.03MB vs 26451.1's ~973KB (+60KB).

Hypotheses for the build side:
- 109 ilc embeds 26451.109 runtime init (its own coreclr is 109); the
  cross-targeted runtime ref used for the app is 26451.1 — check what
  Microsoft.NETCore.App.Runtime.NativeAOT / ILCompiler.RuntimePack ref the
  109 ilc was built against and whether the app's runtime module metadata
  (RuntimeProductVersionString etc.) matches what the 109 runtime expects.
- Compare startup codegen: objdump/strings diff of the first executed
  functions between the working 26451.1 ilc output and the crashing 109
  output (the +60KB delta is in the runtime init/GC region per .so layout).
- 109 ilc's bundled JIT/runtime .so set (libclrjit_* etc.) vs 26451.1's —
  AOT compile is JIT-free so this is about the runtime library used to link
  the app (the NativeAOT runtime lib, not the JIT).

## SIGSEGV detail (for round-17): faulting frame + instruction

Captured via LD_PRELOAD SIGSEGV handler (gdb/lldb unavailable; ptrace blocked
by the HarmonyOS sandbox). Deterministic 100% repro on the minimal app.

- Signal: SIGSEGV si_code=1 (MAPERR), **si_addr=0x8**
- Stack (app ELF offsets, resolved with app.dbg):
  _start_c -> main -> StartupCodeHelpers::InitializeModules ->
  **TypeManager::GetModuleSection(ReadyToRunSectionType, int*)** (faulting)
- Faulting instruction (objdump .text @0x5becc, GetModuleSection entry):
  `ldr x10, [x0, #8]` with x0==NULL (reads 0x8); next `ldrh w8,[x10,#12]`
- So InitializeModules hands GetModuleSection a **null TypeManager/module
  pointer** in the 109-compiled app; the identical source compiled by the
  26451.1 ilc passes a valid pointer (app runs).
- Nearby init code allocates via RhpNewPtrArrayFast then walks module state;
  the 109 output is ~1.03MB vs 26451.1 ~973KB (+60KB in the runtime
  init/module-metadata region).

Likely root cause for the build side: the 109 ilc links a different
NativeAOT runtime ref (upstream merge moved ILCompiler_publish); the
embedded module/TypeManager metadata (ReadyToRun section table pointers) is
inconsistent, so startup resolves a null module. Compare the +60KB init-data
delta and the NativeAOT runtime lib version between 26451.1 and 26451.109
ilc outputs. Suspects: runtime-ref version skew, or a startup-metadata
codegen regression from the upstream merge (same family as the 27.0-vs-27.1
R2R minor noted in the release).
