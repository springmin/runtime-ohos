# 评估：runtime 的 PR 是否现在全部提上游（2026-10-05）

> 问题：能否**不等 `#132953`**，把 runtime 剩余 PR（N1–N16 + C2/C3 + item 5）**一次性全部提交上游**？
> 依据：fork-sync playbook §2（17 支落地顺序/前置）、rehearsal 文档（09-28：merge-tree 39/39
> CLEAN、rebase 20/21 CLEAN、19 支语义 SAME）、N 组清单（前置检查）、上游现状（#132953 静默 3.7 天）。

## 0. 事实基线

- **依赖结构**：N1–N16 **每支的前置 = ① infra（`#132953` 合并 + `eng/common` 同步）**；C2 另需
  `#132866`、C3 需 `#132866` 答复；item 5（`pal_try_load_library` + 测试 + 文档）在 fork feature 上但未开 PR。
- **基础设施重叠**：`#132953` 本体含 **12 个 infra 提交**；playbook 明示："未合并前给 N 组开 PR
  会把 12 个 infra 提交算进 diff"。
- **就绪度**：演练已做（20/21 支 rebase CLEAN、19 支语义 SAME、0 支重做）；`rehearse2/*` 为 09-23
  产物（滞后 75 提交）**不可直接当 PR head**；正确做法=**post-infra main 上重放**。
- **上游节奏**：`#132953`（已批准、评审项全回应、arcade 前置已清）改派复看后 3.7 天静默；
  `#132827`（已批准）7+ 天未合——**评审带宽是当前瓶颈**。

## 1. 方案 A：维持闸门（先合 #132953，再 rebase 逐支开 PR）— **推荐**

**利**
- **diff 干净**：每支只含自身改动（演练已证 rebase 全 CLEAN/SAME），符合评审期望与 arcade 式去重纪律。
- **CI 可用**：post-infra main 上可直接绿；避免"缺 infra"导致的系统性红。
- **评审资本**：不淹没 `#132953`/`#132827`；先例（OpenBSD/Haiku/SunOS）均为**小步串行**，
  批量压上违背该模型。
- **返工最小**：不需在 #132953 合入后再清理每支的 infra 携带面。

**弊**
- 队列受 `#132953` 节奏制约；若长期不合，N 组停滞（GA 列车风险）。
- 单点依赖（一个 reviewer 的注意力）。

## 2. 方案 B：现在全部提交 — **不推荐**

**利**
- 并行推进；不押注单一闸门；若 #132953 受阻，其余工作仍可见。

**弊**
- **diff 污染**：12 个 infra 提交混进每支 PR；评审者会要求先剥离，等于把同一批 infra 审 16 遍。
- **冲突/返工**：与在审 #132953 面重叠；合并后 16 支需统一 rebase。
- **CI 面**：缺 infra 的基座 → 构建/测试红，首印象差且拥塞 CI。
- **关系风险**：在既有两 PR 静默期批量投递 = 噪音；小众平台移植者的带宽有限（OpenBSD 38 支
  仍靠**单支快速合入**，中位 1.7 天）。
- **无先例支持**：三先例都无"批量压上"模式。

## 3. 方案 C：混合（先提"零 infra 依赖"子集）

- 需 file-level 甄别；但按 playbook 每支前置=①，预期子集为空或极小（≤1–2 支）。
- 若存在（如纯库层、且不触 `eng/` 与 RID 图），可先提；否则 C 退化为 A。

| 触发 | 动作 |

| `#132953` 到 **10-08（周三 CST）** 仍无复看 | ① 轻提醒 @jkoritzinsky（沿用既有评论线程）；② 若再静默 → 请第二 reviewer（BuildArea 其他维护者） |

## 5. 结论

1. **不"全部现在提"**（B ✗）：技术性硬前提（每支前置=#132953）与评审资本都不支持。
2. **维持 A** + 设 **10-08 / 10-15 两个检查点**；到点按对冲表推进。
3. 可选：立刻做 file-level 依赖复核，确认 C 是否存在可先提项（预计空集）。
