# HarmonyOS NEXT 生态评审 40 条（2026-10-22）

> **独立评审稿**（暂不并入其它文档与索引）。依据：本团队 .NET / MAUI on OpenHarmony 移植与桌面应用迁移评估的
> 一手经验（真机 OpenHarmony 7.0.0.105–7.0.0.111 / API 26 / 2in1；多轮 kit 发布与设备验证）。
> 结构：**A. 平台生态评审与修改意见 20 条**；**B. .NET 社区视角可持续演进建议 20 条**。
> 优先级：**P0** 阻断生态 · **P1** 显著摩擦 · **P2** 体验完善。

# A. 平台生态评审与修改意见（20 条）

## A-1 运行时与框架使能

**1. 让"自绘 UI"成为一等公民（输入 / 安全控件 / 粘贴）【P0】**
- 现象：自绘 Entry 的 ArkUI 隐藏输入被 XComponent 面遮挡，长按系统粘贴菜单不可达；`PasteButton`/`SaveButton`
  等安全控件只能嵌入 ArkUI 组件树；自绘框架只能自建浮层 + 文本注入。
- 影响：Flutter / MAUI / Avalonia / Unity 等自绘框架的输入、粘贴、安全控件体验被迫绕路；企业表单/审批场景可用性受损。
- 建议：提供 **NAPI 级安全组件协议**（自绘 surface 可唤起安全控件）或"用户手势上下文内的一次性 pasteboard 读"API；
  发布 **自绘 surface 输入契约**（软键盘几何 / IME composition / 文本事件）。

**2. JIT / 动态代码的公开合规通道【P0】**
- 现象：匿名可执行内存默认全封；debug 域依赖隐藏 `prctl`（非公开接口）；release 域 JIT 需华为发布证书 + ACL；
  手机域无 ACL 申请入口；商用 NEXT 机 JIT 全禁。
- 影响：.NET / Java / JS 等第三方运行时只能 AOT 或解释执行 → 性能与动态能力长期落后；框架特性（动态绑定/XAML 运行期）受限。
- 建议：提供 **按包/按签名授予的可写代码内存权限**；至少对 2in1/开发域给出稳定公开契约；发布 JIT 合规白皮书与验证套件。

**3. 跨平台框架官方支持计划与治理透明【P0】**
- 现象：Flutter / RN 有官方 SIG；.NET 与 Avalonia 的社区移植先后归档；Uno 至今无支持。
- 影响：框架厂商与社区无法形成长期投入预期，生态信任受损。
- 建议：建立 **同级支持矩阵**（Flutter / RN / .NET / Avalonia / Unity）与公开路线图；兼容性测试套件；
  社区移植的捐赠/上游路径与治理规则。

**4. 系统库 / ABI 契约（musl / ICU / Skia / SQLite / EGL）【P1】**
- 现象：musl 兼容已实证（`linux-musl-arm64` 原生资产可直跑）；但系统 ICU 缺失（只能 invariant 回退）、
  Skia 仅存在于 OH 源树未作为公开 SDK 件、SQLite 内部不可链接。
- 影响：跨平台框架与原生库每个都要单独移植/构建，生态移植成本高。
- 建议：发布 **NDK sysroot 契约**（libc/libm/ICU/SQLite/EGL/GLES 的存在与版本策略）+ **官方 Skia 预编译包** +
  musl ABI 兼容说明。

## A-2 企业落地

**5. 企业分发与受管设备（release 签名件直装）【P0】**
- 现象：release-signed hap 直装被拒（`not trusted app source`）；2in1 企业应用无 MDM/企业证书式受控分发。
- 影响：企业 LOB 应用（制造、办公、行业系统）即使完成适配也无法落地部署。
- 建议：提供 **企业签名 / 私有应用市场 / 设备所有者信任锚**；受管设备白名单与安装接口。

**6. 企业集成能力缺口（打印 / 工业协议 / 媒体）【P1】**
- 现象：无桌面打印栈（报表受阻）；工业协议（IPC-CFX / OIB 类）无官方 SDK；镜像 MediaKit 缺席；DRM/EME 无。
- 影响：制造与办公类应用迁移卡在"最后一公里"。
- 建议：补齐 **打印框架**（IPP/CUPS 兼容）、**工业协议 SDK**、**MediaKit/DRM 第三方可用形态**。

**7. 无障碍动作 e2e 与自动化【P1】**
- 现象：影子树/provider 可用（节点/语义可读），但动作 e2e 受镜像限制（第三方扩展服务不可启用）。
- 影响：无障碍自动化测试与企业合规验收困难。
- 建议：开放 **无障碍自动化 API**；开发镜像允许第三方扩展服务；提供 a11y CTS 套件。

**8. 多设备 / 2in1 一致性【P1】**
- 现象：手机 / 平板 / 2in1 在软键盘、窗口、输入、a11y 能力上不一致（2in1+物理键盘不弹软键盘等）。
- 影响：一码多端体验割裂，跨形态应用适配成本高。
- 建议：统一 **能力查询 API**；设备形态测试矩阵；模拟器覆盖 2in1/平板/手机。

## A-3 开发体验

**9. ACL 受限权限：透明化、可预检、可分阶段【P0】**
- 现象：受限权限声明即装机失败；ACL 申请仅控制台人工审批、SLA 不明；开发期无法自测获批路径。
- 影响：功能规划与排期不可预期，行业应用迁移信心受损。
- 建议：公开 **ACL 目录**（权限→等级→材料模板→SLA）；开发态允许"声明但运行时拒绝"而非装机失败；
  提供 **CLI/CI 预检**。

**10. 官方完整开发镜像 + 能力矩阵【P1】**
- 现象：开发镜像缺 hilog NDK / ICU / MediaKit，a11y 服务不可启用；签名策略随版本变化（.105 vs .111）。
- 影响：开发者误判平台能力、排查成本高。
- 建议：发布 **官方完整开发镜像**（hilog/ICU/MediaKit/a11y 齐备）+ **镜像能力矩阵**；关键 policy 提供 CI 可配置开关。

**11. 工具链 / CI 可靠性（hdc / 设备）【P1】**
- 现象：沙箱下默认 hdc 看不到设备（需补丁/特殊路径）；设备端口随重启漂移；多 hdc server 并存；锁屏拦截 `aa start`。
- 影响：自动化与 CI 成本高，中小团队易被劝退。
- 建议：稳定 **hdc 协议/端口/重连语义**；提供 **headless CI 模式**（自动解锁/常亮/免 UI 授权）；官方 device farm API。

**12. 调试与可观测性【P1】**
- 现象：缺官方符号化 / EventPipe / 结构化日志路径（需自建）。
- 影响：线上问题定位难，跨语言栈（.NET/Flutter/RN）尤甚。
- 建议：开放 **native 符号服务器**、perfetto 类采样工具、结构化日志标准与崩溃聚类。

**13. 包管理与原生库生态（OHPM / NAPI）【P1】**
- 现象：OHPM 库数量与质量不足；常用 native 库（Skia/SQLite/ICU/OpenSSL）无预编译矩阵；NAPI 绑定工具链不统一。
- 影响：常用库每个都要单独移植/绑定，生态复用度低。
- 建议：官方维护 **常用 native 库 OHOS 预编译矩阵** + 绑定生成器 + SBOM/许可证检查。

**14. 热更新 / 动态化政策【P2】**
- 现象：企业动态化需求与平台安全约束冲突，政策与能力不明确。
- 影响：企业发布灵活性与合规成本不确定。
- 建议：明确热更新允许范围与审核规则；提供官方分包/动态化方案。

**15. 应用体积 / 启动性能工具【P2】**
- 现象：AOT 件体积大（整套 kit 约 70MB 量级）；缺官方 size/startup 预算工具。
- 影响：上架成本与体验优化缺依据。
- 建议：提供体积分析、按需加载/拆包、AOT/PGO 优化指引与公开基准数据。

## A-4 生态与商业

**16. 商店政策与开发者经济【P1】**
- 现象：审核时效、企业专区、分成、隐私标签规则不够透明。
- 影响：ISV 投入回报不可预期。
- 建议：公开 **审核 SLA**、企业应用专区分发、沙盒测试通道、透明分成与隐私标签规范。

**17. 文档 / 示例 / 本地化【P2】**
- 现象：中文先行、英文滞后；官方样例未覆盖跨平台框架（.NET/Avalonia/Uno）。
- 影响：海外与跨栈开发者上手难。
- 建议：双语同步、官方 samples 仓库覆盖主流框架、开发者认证体系。

**18. 开源治理与上游路径【P1】**
- 现象：社区移植缺乏稳定上游化通道（Avalonia 社区移植归档事件影响信任）。
- 影响：社区与框架厂商长期投入意愿受损。
- 建议：以 **SIG 方式**接纳第三方框架/库进入官方发布；明确贡献流程、IP 与许可政策。

**19. 安全与隐私开发者体验【P1】**
- 现象：权限、隐私清单、数据安全标签分散，构建期缺少统一检查。
- 影响：合规成本高、易踩坑。
- 建议：统一隐私清单格式、构建期隐私检查、最小权限默认（ACL 子集思路）。

**20. 兼容性治理：矩阵 / 变更日志 / CTS / compat 开关【P2】**
- 现象：跨版本行为变化无集中清单（签名策略、data: URL 裸 `#`、wasm MIME、剪贴板、JIT/exec-mem）。
- 影响：每次升级"踩雷式"适配。
- 建议：发布 **兼容性矩阵（API × 设备形态 × 镜像策略）** + **行为破坏变更日志** + 第三方 **CTS** + compat 开关。

# B. .NET 社区视角：可持续演进建议（20 条）

> 基线：本团队已完成的优化移植（CoreCLR/AOT + CG2-R2R + 解释器、ASP.NET Core 运行时包、MAUI 平台切片与壳/host、
> 安装包/版本门禁、设备轮与长稳验证）。以下均为**平台侧应做**，以让 .NET 生态在 HarmonyOS NEXT 上长期可持续。

**1. 官方 RID 与 Runtime Pack**
- 现状：OHOS 只能靠自建 workload/bundle，NuGet 生态默认不认 `openharmony-*` RID。
- 建议：把 `openharmony-arm64`（及 x64）纳入官方 RID 图与 runtime pack 发布。

**2. JIT 合规权限（.NET 篇）**
- 现状：JIT 依赖可写可执行内存，当前只能 AOT/解释。
- 建议：按包/按签名授权的 JIT 通道；否则 .NET 在 NEXT 上永久 AOT-only。

**3. 官方 AOT/ILC 工具链**
- 现状：跨平台 AOT 需自建绕行。
- 建议：`Microsoft.DotNet.ILCompiler` 的 OHOS 目标、跨平台 AOT 与稳定 AOT 缓存。

**4. NuGet NativeAssets for OHOS**
- 现状：SkiaSharp/HarfBuzz/SQLite/OpenSSL/ICU 等无 OHOS RID 资产（musl 资产已实证可跑）。
- 建议：官方/社区共建 `openharmony-*` native 资产矩阵。

**5. 系统 ICU / 全球化**
- 现状：系统 ICU 缺失，只能 `InvariantGlobalization` 回退。
- 建议：提供系统 ICU 或官方 ICU 包。

**6. EventPipe / 诊断官方支持**
- 现状：dotnet-trace/dump/counters 无官方 OHOS 支持，需自建符号化与长稳取证。
- 建议：EventPipe socket 权限、dump 采集与符号化官方路径。

**7. 远程调试与热重载**
- 现状：缺官方调试器/Hot Reload（以自建 devloop 替代）。
- 建议：VS/VS Code 的 OHOS 调试器（vsdbg）与 Hot Reload 官方支持。

**8. 工具链一等支持**
- 现状：/tmp UDS 限制、csc 活锁等需看门狗与 `DOTNET_PROCESSOR_COUNT` 绕行。
- 建议：官方稳定性修复/指南，MSBuild/csc 在 OHOS 的一等支持。

**9. 官方 SDK / Workload 发行与更新通道**
- 现状：自建 sdk-ohos 发布与版本锚点。
- 建议：dotnet-install/官方 feed 支持 OHOS，明确版本兼容矩阵。

**10. MAUI 官方平台目标**
- 现状：平台切片/套件为自建。
- 建议：`net11.0-openharmony` TFM 进入官方 MAUI（模板/控件/测试），社区可贡献现有实现。

**11. ASP.NET Core / Blazor 官方支持**
- 现状：运行时包已验证可用，但无官方 RID/模板。
- 建议：Server 与 Blazor Hybrid 的官方支持（含自托管服务指南）。

**12. 测试栈支持**
- 现状：上游单测可跑，但 VSTest/testhost 在 OHOS 沙箱不可用。
- 建议：官方 VSTest / Microsoft.Testing.Platform / testhost 支持。

**13. 性能工程指引与数据**
- 现状：自建 AOT 启动、CG2-R2R、解释器三形态与基准。
- 建议：PGO/R2R/AOT 体积与启动的官方指南、基准与预算工具。

**14. NuGet 安全 / 离线行为**
- 现状：需关闭签名校验、企业私服/离线场景需自解。
- 建议：规范 OHOS 上签名校验、离线 feed、企业私服行为。

**15. 后台服务 / 常驻托管**
- 现状：Ability 生命周期模型与桌面服务模型差异大。
- 建议：提供 systemd 类服务托管等价方案（常驻/自启/看护），服务端 .NET 应用可直接落地。

**16. 模拟器与设备农场**
- 现状：自建设备锁、hdc 重连与守望。
- 建议：官方 OHOS 模拟器/远程设备与 CI 集成（.NET 开发可用）。

**17. 上游化路径**
- 现状：长期 fork 维护（runtime/aspnet/sdk/maui 多仓）。
- 建议：明确 dotnet/runtime 平台支持提案/SIG 路径、许可证与治理，避免永久分叉。

**18. 企业迁移指引与合作**
- 现状：WinForms/WPF 无官方迁移路径；企业 LOB 是最大市场。
- 建议：华为与 Microsoft/.NET Foundation 建立合作渠道，发布 WinForms/WPF→MAUI/Blazor 官方迁移指引。

**19. 官方文档位与双语**
- 现状：".NET on HarmonyOS" 仅有社区/自建文档。
- 建议：dotnet 文档站与华为开发者文档的正式页面与双语同步。

**20. 长期维护承诺**
- 现状：.NET 年度节奏与 OHOS API level 节奏需人工对齐。
- 建议：发布版本对齐、LTS 策略、ABI/CTS 兼容承诺，给社区与 ISV 可预期维护窗口。
