# OpenHarmony 11.0.0 GA release preparation (2026-11-10)

`.NET 11.0.0` / SDK `11.0.100` reached GA on 2026-11-10. This note records the
VMR source mapping and the release branches prepared in the three product
forks. It lives on `runtime-ohos release/ohos-11.0.0`.

## Upstream mapping

The authoritative VMR tag is `dotnet/dotnet v11.0.100` (`.NET 11.0.0 /
11.0.100`, published 2026-11-10T13:50Z).

| Component | Version | VMR source commit | Codeflow PR |
| --- | --- | --- | --- |
| runtime | 11.0.0 | `deae2e32bf0e018e09d64597b7c59b62b73bb3ce` (`release/11.0`) | `dotnet/dotnet#10365` |
| sdk | 11.0.100 | `4ca68185f5faef068d06176a1e3a241f0a7c4041` (`release/11.0.1xx`) | `dotnet/dotnet#10366` |
| aspnetcore | 11.0.0 | `1def4cdc07dc10fc267136060e3ef5c1a96d4a99` (`release/11.0`) | `dotnet/dotnet#10332` |

The VMR carries post-codeflow GA hotfixes on top of those commits:

- runtime: `6e89f3700532` (MsQuic), `79b4b9f11737` (Brotli 1.1.1)
- sdk: `297acf930fb0` (telemetry fast shutdown), `c74bfe72b9e7` (clean VSTest import)
- aspnetcore: `499bce0519b3` (SignalR auth refresh), `524a6a4df8b2` (Kestrel literal `#`)

Those commits exist in the VMR tree but not in the codeflow commits above; a
byte-for-byte VMR match therefore needs them ported (or confirmed as VMR-only).

Status: the sdk telemetry hotfix (`297acf9`) is ported to
`sdk-ohos release/ohos-11.0.100` as `e0e74bd776`. The runtime Brotli/MsQuic and
the aspnetcore SignalR/Kestrel hotfixes remain pending: the diffs touch code
that has diverged in the forks, so they need an owner review rather than a
blind copy.

`sdk-ohos` and `aspnetcore-ohos` already sit on the GA codeflow commit
(`merge-base feature/openharmony <GA commit>` is the GA commit itself), so the
branch is GA plus the OpenHarmony work. `runtime-ohos` is different: the rc3
line is based on an older main snapshot and is 66 commits behind the GA
`release/11.0` tip (`deae2e3`).

## Runtime GA merge (resolved, upstream-first on conflicts)

`deae2e32bf0e` was merged into the rc3 line. The eight conflicts were resolved
by taking the GA version for the seven files whose rc3 side was main-line only
(R2R tests, stubhelpers, number parsing, HPKE) and, for `NamedMutex.Unix.cs`,
taking the GA layout and re-applying the single OpenHarmony exclusion
(`!OperatingSystem.IsOpenHarmony()` in `UsePThreadMutexes`). Merge commit:
`f46d10d19c7`.

## GA build and AOT mirror (2026-11-11)

The runtime/aspnetcore GA build succeeded in `ohos-full-build` run
`42955469729` with `skip_sdk=true` (the SDK packaging stage is separate).
The runtime product version is `11.0.0-rtm.26529.118` (GA build id
`20261029.118`).

The two GA AOT packages were published to the `aot-packs-11.0.0` mirror:

- `Microsoft.NETCore.App.Runtime.NativeAOT.openharmony-arm64.11.0.0-rtm.26529.118.nupkg`
- `runtime.openharmony-arm64.Microsoft.DotNet.ILCompiler.11.0.0-rtm.26529.118.nupkg`
- `SHA256SUMS`

`sdk-ohos release/ohos-11.0.100` maps the `11.0.0` line to that mirror
(`versions.env` tag/assets/pins). The offline AOT resolution test passes
19/19, and the real `ohos-install-tests` workflow is green
(run `42964768045`).

The full SDK redist build (without `skip_sdk`) still fails on the custom
runtime version: it requests `Microsoft.NET.ILLink.Tasks` and host runtime
packs for RIDs such as `win-x86` at `11.0.0-rc...` that the OpenHarmony build
does not produce. This is a separate SDK packaging task; it does not block the
runtime/aspnetcore GA build or the AOT mirror.

## Verification status

- Static: no conflict markers; the ported SignalR C# source files match the
  VMR GA tree; the Kestrel diffs against the VMR are limited to the fork's
  existing divergences (`EnableChunkedExtensions`, main-line flow-control
  code).
- Build: runtime + aspnetcore passed on the GitHub runner (run `42955469729`).
  The host `dotnet restore` stall only affects local probing; the CI runner is
  the authoritative build path. The SDK redist stage remains blocked as noted
  above.
