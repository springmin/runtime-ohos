# OpenHarmony 11.0.0 GA release preparation (2026-11-10)

`.NET 11.0.0` / SDK `11.0.100` reached GA on 2026-11-10. This note records the
VMR source mapping and the release branches prepared in the three product
forks. It lives on `runtime-ohos release/ohos-11.0.0`.

## Upstream mapping

The authoritative VMR tag is `dotnet/dotnet v11.0.100` (`.NET 11.0.0 /
11.0.100`, published 2026-11-10T13:50Z).

| Component | Version | VMR source commit | Codeflow PR |
| --- | --- | --- | --- |
| runtime | 11.0.0 | `deae2e32bf0e018e09d64597b7c59b62b73bb3ce` (`release/11.0`) | `dotnet/dotnet#10365` |
| sdk | 11.0.100 | `4ca68185f5faef068d06176a1e3a241f0a7c4041` (`release/11.0.1xx`) | `dotnet/dotnet#10366` |
| aspnetcore | 11.0.0 | `1def4cdc07dc10fc267136060e3ef5c1a96d4a99` (`release/11.0`) | `dotnet/dotnet#10332` |

The VMR carries post-codeflow GA hotfixes on top of those commits:

- runtime: `6e89f3700532` (MsQuic), `79b4b9f11737` (Brotli 1.1.1)
- sdk: `297acf930fb0` (telemetry fast shutdown), `c74bfe72b9e7` (clean VSTest import)
- aspnetcore: `499bce0519b3` (SignalR auth refresh), `524a6a4df8b2` (Kestrel literal `#`)

Those commits exist in the VMR tree but not in the codeflow commits above; a
byte-for-byte VMR match therefore needs them ported (or confirmed as VMR-only).

## Prepared branches

| Fork | Branch | Base | Notes |
| --- | --- | --- | --- |
| `runtime-ohos` | `release/ohos-11.0.0` | `release/ohos-rc3` (`b3b3d3cff49`) | version label switched to `rtm`; GA merge pending |
| `sdk-ohos` | `release/ohos-11.0.100` | `feature/openharmony` | `versions.env` pinned to GA; base contains `4ca68185` |
| `aspnetcore-ohos` | `release/ohos-11.0.0` | `feature/openharmony` | version label switched to `rtm`; base contains `1def4cdc` |

`sdk-ohos` and `aspnetcore-ohos` already sit on the GA codeflow commit
(`merge-base feature/openharmony <GA commit>` is the GA commit itself), so the
branch is GA plus the OpenHarmony work. `runtime-ohos` is different: the rc3
line is based on an older main snapshot and is 66 commits behind the GA
`release/11.0` tip (`deae2e3`).

## Runtime GA merge status

A merge of `deae2e32bf0e` into `release/ohos-rc3` was attempted and aborted to
keep the release branch clean. It conflicts in eight files that carry
OpenHarmony changes:

- `src/coreclr/tools/aot/ILCompiler.ReadyToRun.Tests/TestCasesRunner/R2RResultChecker.cs`
- `src/coreclr/tools/aot/ILCompiler.ReadyToRun.Tests/TestCasesRunner/R2RTestRunner.cs`
- `src/coreclr/vm/stubhelpers.cpp`
- `src/coreclr/vm/stubhelpers.h`
- `src/libraries/Common/src/System/Number.Parsing.Common.cs`
- `src/libraries/System.Private.CoreLib/src/System/Number.Parsing.cs`
- `src/libraries/System.Private.CoreLib/src/System/Threading/NamedMutex.Unix.cs`
- `src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/HpkeKemMetadata.Managed.cs`

Resolving them requires the owners of the corresponding OpenHarmony patches;
the branch is intentionally left at the rc3 tip plus the `rtm` version pin.

## Next steps

1. Resolve the runtime GA merge on `release/ohos-11.0.0` and verify the runtime
   build/tests.
2. Port the VMR GA hotfixes listed above, or record why they are not needed
   for the OpenHarmony artifacts.
3. Refresh the OpenHarmony workload bundle pin when the GA-compatible bundle
   is published (`sdk-ohos eng/ohos-install/versions.env`).
4. Run the usual HAP/device release gates before tagging `11.0.0-ohos`.
